# What 89 tests on a local signer prove, and what they don't

[`acta-ordia-signer`](https://github.com/Veritas-Systems-Tech/acta-ordia-signer) is the desktop helper described in [the signer design note](local-pki-signer.md). Its test suite has 85 unit tests and 4 updater integration tests, and `cargo test` passes all 89. This note says what that number covers by listing the test groups, and where the suite stops.

## What the tests cover

- **Who may call the signer (about 10 tests).** The origin allowlist accepts exact matches only, and rejects a missing origin, an unlisted one, a lookalike and a substring match. The development port is allowed only in debug builds. A disallowed origin is rejected before any signing code runs. An origin alone cannot reach a successful `/sign`, because browsers set it but other local programs can send any header. A regression test replays the full signing-oracle flow and expects it to fail.
- **What the backend's signature binds (about 12 tests).** `/sign` rebuilds a tagged message from the request and verifies the Ed25519 signature over it. A good message passes. A wrong session id, an altered digest, an altered expiry, a claimed fingerprint that differs from the signed one, a signature over the bare digest, a wrong or missing domain prefix, a signature from another key, an expired message and a missing protocol version each fail with a static error code. A rejected request does not consume the session. A malformed body gets a static error that does not echo the offending value, and a clock that cannot be read fails closed instead of skipping the expiry check.
- **Cross-language vector (1 test per language).** The same fixed inputs, throwaway seed, message bytes and signature are checked in the Rust tests and in the backend's TypeScript tests, so a layout or endianness mismatch between the two fails a test. The expiry in the vector uses the high half of the 64-bit field, and the TypeScript builder cannot take values above 2^53, so the vector is `0x0001020304050607`.
- **Which certificate signs (2 tests).** The fingerprint in the signed message has to equal the SHA-256 of the certificate unlocked at the prepare step. Another test checks that fingerprint helper against a known vector.
- **What the user sees (about 8 tests).** Document titles are stripped of control and bidirectional characters and capped in length. A certificate subject name from a malicious certificate is sanitized before it appears in the confirmation dialog.
- **Error text (5 tests).** The helpers behind the prepare step return static messages for an unreadable file, a nonexistent path and a file that is not a certificate, and the tests assert that the response contains no path, no OS error text and no OpenSSL text. The prepare handler itself needs a live GUI dialog, so those tests cover the helpers and the response builder, not the handler.
- **Robustness (about 6 tests).** An oversized body is capped with a 400, a malformed fingerprint is rejected with a static message, an unknown session returns 404, an unknown route returns 404, and `/health` still answers during a slow concurrent prepare.
- **Signing and key handling.** The RSA signing step is deterministic per key and input, differs across keys, and produces a signature that verifies. The embedded production public key parses. The agent token is random and 32 bytes long. The passphrase and session-state modules have their own tests.
- **Updates (4 integration tests).** The updater finds a correctly signed newer release, reports no update when the remote version is not newer, rejects a tampered artifact, and rejects a release signed with the wrong key.
- **Crash reports (4 tests).** The function that scrubs a Sentry event before it is sent drops the machine's hostname and replaces a panic's message with a fixed string, so a path inside the message does not go out. It leaves a static error code alone and leaves a non-panic exception's text alone.
- **Configuration guards (3 tests).** One checks that the Tauri global is enabled, one that the run closure still prevents exit, and one that the passphrase page actually uses the global its own test depends on, so a refactor cannot silently turn that test into a no-op.

## What they do not cover

- A real ICP-Brasil certificate has never been used. The mechanism is tested with a throwaway key and a self-signed certificate, so I do not know that the backend accepts what the signer produces for a real one.
- The unlock step needs a file picker and a passphrase dialog, so no test drives it. The fingerprint of the certificate that was actually unlocked is exercised only through the lower-level pieces.
- The suite runs the HTTP server in process. It does not test the web app, the backend and the signer together. Only the shared message vector links the two sides, so a mismatch that the vector does not capture would show up first in production. An end-to-end test is the obvious addition, and it is on my checklist.
- The scrub tests call the scrub function directly. Nothing drives a real panic through Sentry's hook inside the running app, so the wiring between the two is checked by reading the code and by a one-off probe, not by a test.
- There is no GUI click-through on macOS or Windows. CI builds and runs the headless tests on all three.
- Tests prove that known bad inputs are rejected. They do not prove there is no other way to get a signature, and the signer still signs any digest the backend vouches for within the expiry window. Closing that gap is a design change, not a test: the signer should be able to check what it signs without trusting the backend, and that is on my roadmap (see [the signer design note](local-pki-signer.md)).

All 89 tests run on every build, so the properties listed above are re-checked each time. A property nobody thought to test is not covered by that count.
